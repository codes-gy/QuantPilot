# 📱 QuantPilot 프론트엔드 기획서

> 백엔드는 인증/주문 파이프라인/리스크 가드/체결 확인 폴링까지 상당히 완성되어 있는 반면,
> 프론트엔드는 화면 골격과 네비게이션만 잡혀 있고 **6개 화면 중 3개(로그인/주문 내역/설정)가
> 자리표시자(placeholder)** 상태입니다. 이 문서는 현재 상태를 정확히 정리하고, 무엇을 어떤
> 순서로 채울지 기획하는 것이 목적입니다.

### 네트워크 레이어의 미완성 지점
- `ApiClient`(Dio): 401 응답을 받아도 **토큰 삭제/로그인 화면 이동이 안 됨** (인터셉터에 TODO로 표시됨)
- `LiveWsClient`: 연결 끊기면 **항상 고정 3초 뒤 재연결** (지수 백오프 없음, TODO로 표시됨)

### 이미 잘 잡혀 있는 것 (그대로 유지)
- **아키텍처 패턴**: `feature/data`(Repository + Riverpod Provider) · `feature/domain`(모델) ·
  `feature/presentation`(화면) 3계층 분리가 일관되게 지켜지고 있음 — 새 화면도 이 패턴을 따르면 됨
- **테마**: Material 3, 라이트/다크 모두 시드 컬러(진한 그린, `0xFF1B5E20`) 기반 구성 완료
- **실시간 시세**: `/ws/live` 구독 → `priceTickStreamProvider`로 심볼별 필터링하는 패턴이 이미
  검증되어 있어서, 주문 상태 실시간 업데이트 등에도 그대로 재사용 가능

## 2. 정보구조 / 네비게이션 재정비

### 문제
현재 `main.dart`는 로그인 여부를 전혀 확인하지 않고 곧장 4탭 `RootShell`을 보여줍니다. 토큰이
없는 상태로 API를 호출하면 401만 반복해서 받게 되는 구조입니다.

### 제안하는 흐름
```
앱 시작
  └─ secureStorage에 access_token 존재?
       ├─ 없음  -> LoginScreen
       │            └─ 로그인 성공 -> 토큰 저장 -> RootShell
       └─ 있음  -> RootShell (기존 4탭 그대로: 대시보드/전략/주문/설정)
                     └─ API 401 응답 수신 -> 토큰 삭제 -> LoginScreen으로 강제 이동
```
`MaterialApp`의 `home`을 조건부로 바꾸기보다는, 토큰 유무를 감시하는 Riverpod
`StateNotifierProvider`(또는 `AsyncNotifier`) 하나를 루트에 두고, 그 상태에 따라
`LoginScreen`/`RootShell`을 스위칭하는 방식을 권장합니다 (401 인터셉터가 이 provider의 상태를
직접 바꿀 수 있어야 하므로).

## 3. 화면별 상세 기획

### 3.1 로그인 (최우선 — 없으면 앱 자체를 못 씀)
- **목적**: `POST /auth/login`으로 access_token 발급받아 `secureStorageProvider`에 저장
- **구성 요소**: 이메일/비밀번호 입력 필드, 로그인 버튼, 에러 메시지 영역(자격증명 오류/네트워크 오류 구분)
- **참고**: 백엔드에 공개 회원가입 엔드포인트가 없음(`backend/README.md`) — 계정은 CLI
  스크립트(`scripts/create_user.py`)로만 생성되므로, 이 화면에 회원가입 링크는 불필요
- **연동**: `AccountRepository.login(email, password) -> accessToken`, 성공 시
  `secureStorage.write(key: 'access_token', ...)` 후 루트 상태 갱신

### 3.2 대시보드 — ✅ 완료
- **목적**: 앱을 열자마자 "지금 상태가 괜찮은지" 한눈에 보여주는 화면. 이미 있는 비상 정지 버튼과
  자연스럽게 연결되어야 함
- **채운 것**:
  - 오늘 실현손익 및 일일 손실 한도 대비 현황 (`GET /risk/daily-pnl`)
  - kill switch 발동 중일 때만 보이는 빨간 배너 + 배너에서 바로 해제 가능 (`GET /risk/kill-switch`,
    `POST /risk/kill-switch/release`) — 평소엔 안 보이고, 발동 시에만 나타남
  - 보유 포지션 요약, symbol별 수량/평단가 (`GET /positions`)
  - 당겨서 새로고침으로 세 가지를 한 번에 갱신
- **남은 것**: kill switch 발동 이력(`GET /risk/kill-switch/history`)은 아직 대시보드에 안
  붙였음 — 우선순위 낮지만 붙이기 쉬움 (알림을 놓쳤을 때 앱만 열면 바로 확인하고 싶을 때 유용)

### 3.3 내 전략 (이미 구현됨 — 개선 여지)
- **현재**: 목록 조회만 가능, 상세/생성/수정 불가
- **채워야 할 것**:
  - 전략 상세 화면 (entry_rule/exit_rule/max_position_size/stop_loss_pct 확인)
  - 전략 생성/수정 폼 (이미 코드에 TODO로 "생성 화면으로 이동하는 FAB" 표시되어 있음)
  - 전략별 상태 변경(활성/일시정지) 액션
- 백엔드에 CRUD 엔드포인트가 이미 있는지 확인 후, 없으면 백엔드 작업이 선행되어야 함

### 3.4 시세 (이미 구현됨 — 매우 단순한 상태)
- **현재**: 심볼 하나의 현재가만 숫자로 표시
- **채워야 할 것**:
  - 관심 종목 목록(여러 심볼)을 관리하고 탭에서 리스트로 보여주기 — 지금은 화면 진입 시
    `symbol`을 파라미터로 받아야만 접근 가능한 구조라, 목록 자체가 없음
  - 가격 변동 방향(상승/하락) 색상 표시, 등락률
  - (선택) 간단한 차트 — `fl_chart`가 이미 의존성에 있음 (아직 어디서도 쓰이지 않음)

### 3.5 주문 내역 — ✅ 완료 (당겨서 새로고침 방식)
- **목적**: 체결 확인 폴링(백엔드에 최근 추가됨)으로 갱신되는 주문 상태를 보여주기
- **구현하면서 계획 수정**: 원래 `/ws/live`로 실시간 반영을 계획했는데, 실제로는 **백엔드가 주문
  상태 변경을 WS로 브로드캐스트하지 않고 있었습니다** (시세/리스크 알림만 브로드캐스트됨). 그래서
  지금은 화면 진입 시 조회 + 아래로 당겨서 새로고침(pull-to-refresh) 방식으로 구현했습니다.
  실시간 반영이 필요해지면 백엔드에 주문 이벤트 브로드캐스트를 먼저 추가해야 합니다.
- **연동**: `GET /orders` (`OrderRepository.list_recent`)
- **표시 항목**: 심볼, 방향(매수/매도, 국내 증권가 관례로 매수=빨강/매도=파랑), 수량, 체결 수량,
  상태(대기/접수됨/체결완료/부분체결/거부됨/취소됨 한글 라벨), 모의투자 여부 배지

### 3.6 설정
- **목적**: 지금 거래 모드(모의/실전)를 조회 전용으로 보여주기 — **주의: `TRADING_MODE` 전환은
  앱에서 하지 않는다** (코드 주석에 이미 명시됨, 백엔드 `.env`에서만 전환). 실수로 앱에 토글
  버튼을 넣지 않도록 주의
- **채워야 할 것**:
  - 현재 거래 모드 배지 (`GET /health`가 `trading_mode`를 이미 응답에 포함하고 있어 바로 재사용 가능)
  - 로그아웃 버튼 (토큰 삭제 + 로그인 화면 이동)
  - (선택) 알림 채널 관련 설정 — 백엔드가 아직 앱 웹소켓 채널 하나뿐이라, 이메일/푸시가 추가되기
    전까지는 우선순위 낮음

## 4. 네트워크 레이어 보완 (화면 작업과 병행 권장)

| 항목 | 현재 | 해야 할 것 |
| :--- | :--- | :--- |
| 401 처리 | ✅ 완료 (`ApiClient.onUnauthorized` 콜백 + `authStateProvider`) | - |
| WS 재연결 | ✅ 완료 (1s → 2s → 4s → ... 최대 30초, 메시지 수신 시 리셋) | 실패 횟수가 계속 쌓일 때 사용자에게 알려주는 UI는 아직 없음 (선택 사항) |

이 둘은 특정 화면에 종속되지 않는 공용 인프라라, 로그인 화면 작업과 함께(또는 직후) 처리하는
것을 권장합니다 — 로그인 플로우 자체가 "토큰 없음/만료 시 어떻게 되는가"에 크게 의존하기 때문입니다.

## 5. 우선순위 로드맵

| 순서 | 작업 | 이유 | 상태 |
| :--- | :--- | :--- | :--- |
| 1 | 로그인 화면 + 인증 상태 분기(2절) + 401 처리 | **이게 없으면 앱을 아예 못 씀** — 가장 시급 | ✅ |
| 2 | WS 재연결 백오프 | 로그인과 맞물려 작업하기 좋은 타이밍 | ✅ |
| 3 | 대시보드 채우기 (오늘 손익, kill switch 상태 배지) | 앱의 "얼굴"이자 이미 있는 백엔드 엔드포인트로 바로 채울 수 있음 | ✅ |
| 4 | 주문 내역 화면 | 체결 확인 폴링이 막 완성된 백엔드 기능이라, 눈으로 확인할 화면이 있으면 좋음 | ✅ (당겨서 새로고침, WS 실시간 반영은 백엔드 브로드캐스트 추가 후) |
| 5 | 설정 화면 (거래 모드 표시 + 로그아웃) | 작고 간단 | 🟡 로그아웃 버튼만 (1번 작업 중 함께 추가) |
| 6 | 전략 생성/수정 폼, 시세 관심종목 목록/차트 | 규모가 크고 백엔드 작업이 추가로 필요할 수 있어 후순위 | ⬜ |

## 6. 공통 원칙 (새 화면 작업 시 지켜야 할 것)

- 새 feature는 기존과 동일하게 `data/`(Repository + Provider) · `domain/`(모델) ·
  `presentation/`(화면) 3계층으로 구성
- API 호출은 반드시 `ApiClient`(`apiClientProvider`)를 거친다 — JWT 첨부가 자동으로 되기 때문
- 실시간 데이터가 필요하면 `liveWsClientProvider`의 스트림을 `where`로 필터링하는 기존 패턴
  (`priceTickStreamProvider` 참고) 재사용
- `TRADING_MODE`처럼 백엔드 `.env`로만 제어되어야 하는 값은 앱에서 조회만 하고 변경 UI를 만들지 않는다
